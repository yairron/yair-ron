# סקריפטי תיקיית מסלולי האופניים - `route_catalog`

תיעוד לשלושת הסקריפטים שנמצאים בתיקייה הזו, ובמיוחד לסקריפט המרכזי החדש
`build_routes_catalog.py`. נכתב כדי שיהיה ברור מה כל סקריפט עושה, מה הוא מפיק,
ומה עדיין פתוח/לא הוחלט לגבי המשך הפרויקט.

## שלושת הסקריפטים, ומה הקשר ביניהם

```
gpx_analyzer.py            - קיים מקודם. מסווג כל קובץ: סוג פעילות (הליכה/רכיבה),
                              וסוג מקור (הקלטה בפועל / תכנון מסלול), לפי היוריסטיקות
                              (מהירות ממוצעת, צפיפות נקודות, timestamps, creator).
                              מריצים לבד: python gpx_analyzer.py

gpx_meaningful_rename.py   - קיים מקודם. משנה שם לקבצים שאין להם "מילה משמעותית"
                              בשם (למשל timestamp גולמי) - לפורמט
                              <תאריך>_<עד 3 ישובים קרובים>.gpx, לפי מאגר ישובים
                              (support_data/city.csv). קבצים שכבר יש להם שם
                              משמעותי לא נוגעים בהם.
                              מריצים לבד: python gpx_meaningful_rename.py [--dry-run]

build_routes_catalog.py    - חדש. מפעיל את שני הסקריפטים למעלה ומוסיף עליהם -
                              ראו פירוט מלא למטה. זה הסקריפט שרצים אחרי שמוסיפים
                              קבצי GPX חדשים לתיקייה.
                              מריצים: python build_routes_catalog.py [--skip-thumbnails]

import_gpx_batch.py        - חדש (16.08.2026). מייבא קבצי GPX חדשים מתיקיית מקור
                              חיצונית (למשל ייצוא מלא מאפליקציית מעקב) - מזהה כפילויות
                              לפי תוכן (לא שם קובץ) מול מה שכבר קיים, ומנקה extensions
                              מיותרים (דופק/קצב) בהעתקה. לא מריץ בעצמו את
                              build_routes_catalog.py - יש להריץ אותו בנפרד אחרי כן.
                              מריצים: python import_gpx_batch.py "<נתיב למקור>" [--dry-run]
```

חשוב: `build_routes_catalog.py` לא כותב מחדש שום היגיון מהשניים הקיימים - הוא
מייבא אותם (`import gpx_analyzer`, `import gpx_meaningful_rename`) וקורא ישירות
לפונקציות שלהם (`analyze_file`, `load_settlements`, `find_nearby_settlements`,
`extract_date_from_filename` וכו'). שינוי עתידי בהיוריסטיקה של אחד הכלים הקיימים
(למשל שינוי סף המהירות שמבחין בין הליכה לרכיבה) ישפיע אוטומטית גם על הקטלוג,
בלי צורך לעדכן שני מקומות.

## מה בדיוק `build_routes_catalog.py` עושה, שלב אחר שלב

1. **קליטת קבצים חדשים** - מריץ בפועל את `gpx_meaningful_rename.py` (את פונקציית
   ה-`main` שלו, עם פרמטרי ברירת המחדל) על כל קבצי ה-GPX בתיקייה. קבצים חדשים
   שנוספו ידנית ואין להם שם משמעותי משתנים אוטומטית; קבצים קיימים לא נוגעים בהם.
2. **טעינת מאגר הישובים** - פעם אחת, דרך `load_settlements()` הקיים.
3. **ניתוח כל קובץ** - `analyze_file()` הקיים (סוג פעילות, מרחק, סוג מקור), ובנוסף
   שליפת נקודות המסלול המלאות (כולל גובה - ראו סעיף 4).
4. **טיפוס וירידה מצטברים (חדש)** - אף אחד משני הכלים הקיימים לא חישב את זה.
   **תוקן ב-16.08.2026** אחרי דיווח משתמש בפועל: קובץ (`ערד שפך זוהר.gpx`, מסלול
   שכולו ירידה בפועל מערד לים המלח) הראה 659 מ' "טיפוס" - התברר שזה כמעט כולו
   רעש GPS (1,133 מקטעים חיוביים זעירים, הגדול שבהם 3.5 מ' בלבד). הנוסחה המקורית
   (סכימת כל הפרש חיובי/שלילי בין נקודות עוקבות - עדיין הנוסחה בכלי "ניקוי קובץ
   GPX", `YR1/bike/gpx_cleaner/gpx_cleaner.html`, חישוב `trackStats.climb` - לא
   תוקן שם, כלי נפרד ועצמאי) מצטברת מכל רעד קטן כאילו הוא טיפוס אמיתי.
   **הנוסחה החדשה** (`calc_elevation_gain_loss()`) משתמשת בסף-רעש (hysteresis) של
   4 מ' - מתעלמת משינוי גובה עד שהוא חוצה את הסף ביחס לנקודת הייחוס האחרונה.
   אומת מול gpx.studio (כלי חיצוני עצמאי) על אותו קובץ בדיוק: 448 מ' טיפוס / 1377
   מ' ירידה כאן, מול 453/1384 בפועל שם - פער <2%. קובץ בלי תגי `<ele>` בכלל מקבל
   `null` ("אין נתון") בשני השדות, לא אפס - אסור לבלבל בין השניים. שני שדות
   נפרדים בקטלוג: `elevation_gain_m` ו-`elevation_loss_m`.
5. **ישובים סמוכים לכל קובץ** - לא רק לקבצים ששונה שמם בשלב 1: גם קובץ שכבר
   הייתה לו שם משמעותי מקבל כאן רשימת ישובים סמוכים (`find_nearby_settlements()`
   הקיים, עם אותה הרחבת-רדיוס הדרגתית), כדי שדף הקטלוג יוכל לחפש/לסנן לפי מיקום
   גם עבורו.
6. **תמונה ממוזערת (חדש)** - נוצרת בדפדפן אמיתי (Playwright, אותו כלי שכבר
   בשימוש בסקריפטים אחרים באתר תחת
   `BTL/support_files/senior_rights/scripts/`), שמריץ עמוד מפה מקומי
   (`thumbnail_template.html`, לצד הסקריפט) עם אותה שכבת מפה טופוגרפית בדיוק
   שכבר בשימוש בכלי "ניקוי קובץ GPX" (Israel Hiking Map, אותה כתובת טיילים
   ואותה גרסת Leaflet). העמוד נטען פעם אחת בלבד לכל הריצה - לכל מסלול רק
   מציירים עליו קו חדש ומצלמים, בלי לפתוח דפדפן/עמוד מחדש לכל קובץ (משמעותית
   יותר מהיר מריצה עם טעינת עמוד נפרדת לכל קובץ). **מסלול שכבר יש לו קובץ
   תמונה קיים (לפי שם) מדלג לגמרי על הציור/צילום** - כלומר הרצה חוזרת אחרי
   הוספת קבצים בודדים חדשים מהירה משמעותית, כי רק הקבצים החדשים בפועל
   מקבלים תמונה חדשה. אם רוצים לכפות רענון של **כל** התמונות (למשל אחרי שינוי
   עיצוב בתבנית, כמו שקרה עם צבע קו המסלול ב-16.08.2026) - יש להריץ עם הדגל
   `--force-thumbnails`, במקום למחוק ידנית.
7. **ניקוי תמונות יתומות (חדש, 16.08.2026)** - `cleanup_orphan_thumbnails()`,
   רץ אוטומטית בסוף שלב 4 (רק כשלא השתמשו ב-`--skip-thumbnails`): מוחק כל
   קובץ `.png` בתוך `thumbnails/` שאין לו יותר רשומה תואמת בקטלוג. קורה בעיקר
   אחרי ששינו שם לקובץ GPX **ידנית** (לא דרך הסקריפט) - התמונה הישנה, תחת השם
   הקודם, לא הייתה נמחקת בעצמה אחרת (זה בדיוק מה שקרה בפועל עם שינוי השם הידני
   של `fi_E9B8658A-...gpx` ל-`2026-08-11_גורן גדול.gpx` - הריצה הבאה יצרה
   תמונה חדשה תחת השם החדש ומחקה אוטומטית את הישנה).

## פלט

- `route_catalog/data/routes-catalog.json` - קובץ הקטלוג המרוכז. זה מה שדף
  הקטלוג (כשייבנה) יקרא בפועל. לכל מסלול: שם קובץ, נתיב לקובץ ה-GPX המקורי,
  תאריך (ומקור התאריך - שם קובץ / timestamps / תאריך שינוי הקובץ), סוג פעילות
  (הליכה/רכיבה), **סוג מקור** (`source`: "הקלטה" / "תכנון מסלול" / "לא ברור" -
  ראו הערה למטה), מרחק, גובה מצטבר (או `null`), מספר נקודות, רשימת ישובים
  סמוכים, ונתיב לתמונה הממוזערת.

**שדה `source` (נוסף אחרי ההרצה הראשונה):** לפי בדיקה בפועל, כל 27 (מתוך 193)
הקבצים שאין להם נתוני גובה הם קבצי **תכנון מסלול** (נוצרו בכלים שונים ולא
מהקלטה בפועל) - לא הקלטות עם תקלה. לכן, בנוסף ל-`null` בשדה הגובה, כל מסלול
מקבל גם שדה `source` נפרד שמקורו ב-`source_guess` של `analyze_file()` הקיים -
כדי שדף הקטלוג יוכל להציג תגית "תכנון" ברורה, ולא רק "אין נתון" מבלבל בעמודת
הגובה. שימו לב: הכיוון ההפוך לא נכון באותה מידה - יש קבצי תכנון-מסלול שדווקא
*יש* להם נתוני גובה (כנראה מכלי תכנון שמוסיפים פרופיל גובה מבוסס מודל שטח) -
לכן שני השדות (`elevation_gain_m` ו-`source`) נשארים עצמאיים ולא אחד נגזר
מהשני.

## חלוקה ל-5 אזורים גיאוגרפיים (`regions`, 17.08.2026)

המשתמש סיפק מפה של 34 "יחידות נוף" (סיווג גיאוגרפי רשמי, ראו חיפוש שנעשה על
כך בשיחה) - אבל ביקש בפועל **פישוט ל-5 אזורים** מוגדרים לפי גבולות בין ערים
אמיתיות, לא לפי גבולות ה-GIS הרשמיים המדויקים (שלא הצלחתי בפועל להשיג/לגשת
אליהם בזמן שנבדק). כל הגבולות ממומשים כקווים ישרים בין קואורדינטות אמיתיות של
ערים (גבעת עוז, אשקלון, בית גוברין, בית שמש) - ראו `classify_point_region()` ו-
`_side_of_line()` ב-`build_routes_catalog.py` לפירוט המדויק ולקבועי הסף.

**5 האזורים:** רמת הגולן והחרמון, צפון, מרכז, ירושלים ומדבר יהודה, נגב וערבה.

**מסלול שחוצה בין אזורים סמוכים מקבל את כל האזורים שהוא נוגע בהם** (בדיוק לפי
בקשת המשתמש: "ניתן יהיה לשמור לכל מסלול יותר מאזור אחד בתנאי שנושקים") -
`classify_route_regions()` מסווגת כל נקודה נדגמת (`renamer.sample_points()`,
אותו מנגנון דגימה כבר בשימוש לחישוב ישובים קרובים) בנפרד, ומחזירה את **איחוד**
האזורים שנמצאו. זה פותר את דרישת ה"נושקים" בלי מנגנון "רצועת חפיפה" נפרד -
מסלול שנשאר כולו באזור אחד מקבל תגית אחת; מסלול שבאמת חוצה גבול מקבל את שניהם
באופן טבעי, כי חלק מהנקודות הנדגמות נופלות בכל צד.

**פילוח בפועל על 728 המסלולים (17.08.2026):** צפון 566, נגב וערבה 85, ירושלים
ומדבר יהודה 56, רמת הגולן והחרמון 43, מרכז 41 (הסכום גדול מ-728 כי חלק
מהמסלולים חוצים אזורים). אומת ידנית מול כמה נקודות ציון אמיתיות לפני ההרצה
המלאה (חרמון/גולן, גליל מערבי, תל אביב, באר שבע, ירושלים) - כולן סווגו נכון.

**חו״ל (נוסף 30.10.2026):** נקודה מחוץ למלבן שתוחם את ישראל (`ISRAEL_LAT_MIN`
וכו') מסווגת "חו״ל" לפני כל בדיקה אחרת. עד אז מסלולים בחו"ל קיבלו אזור ישראלי
לפי המשך הקווים מעבר לגבולות (בודפשט/וינה/ליידן "צפון", לאוס/נפאל "רמת הגולן"
או "נגב"). 21 מסלולים עברו ל"חו״ל"; אף מסלול בישראל לא השתנה. נוסף גם כאפשרות
בסינון האזור ב-`catalog.html`.

**גבולות צפון ונגב (תוקנו 30.10.2026, לבקשת המשתמש):** "צפון" = כל מה שצפונית
לקו הרוחב של גבעת עוז (`GIVAT_OZ_LAT`; במקום הקו האלכסוני חיפה-בית שאן, שהשאיר
את הכרמל, יגור, שער העמקים ורמות מנשה ב"מרכז"). "נגב וערבה" במערב = מדרום לקו
אשקלון-בית גוברין (במקום אשקלון-בית שמש, שבית שמש עצמה ישבה עליו ונפלה לנגב).
שינוי זה הזיז 35 מסלולים.

**גבול צפוני ל"ירושלים ומדבר יהודה" (תוקן 30.10.2026):** עד אז כל נקודה מדרום
לקו חיפה-בית שאן ומזרחית ל-35.05 נפלה ל"יהודה" - כולל יגור, רמות מנשה, שער
העמקים, עין שמר ויקנעם (15 מסלולים). נוסף `JUDEA_NORTH_LAT_CUTOFF = 32.0`: צפונית
לו השטח הזה מסווג "מרכז", כמו הכרמל שממערב לו. (הבקעה דרומית לבית שאן כבר
מטופלת מ-17.08.2026 ע"י אזור "בקעת הירדן" הנפרד.) **האזורים מחושבים מחדש בכל
הרצה גם למסלולים מהמטמון** (מתוך `_coords` השמור), כך ששינוי גבולות חל מיד על
כל הקטלוג בלי למחוק את המטמון.

**שדה `settlements_found`:** True/False מפורש, לא רק הסתמכות על רשימת
`settlements` ריקה - כדי שדף הקטלוג יוכל להציג תגית ברורה ("מיקום לא זוהה")
במקום עמודת ישובים ריקה לא-מוסברת. `gpx_analyzer.py` הקיים עצמו מחזיר שלושה נוסחים שונים לאותה משמעות
("תכנון מסלול", "תכנון מסלול (route)", "תכנון מסלול (לפי שם קובץ)" - הבדל בין
הענפים בקוד שקבעו את הסיווג) - `normalize_source_guess()` בסקריפט הזה מאחד
את כולם לתווית אחת נקייה לפני הכתיבה לקטלוג, בלי לגעת בקובץ המקורי.
- `route_catalog/data/thumbnails/*.jpg` - התמונות הממוזערות עצמן, קובץ אחד לכל
  מסלול (שם הקובץ + `.jpg`). **JPEG, לא PNG** (שונה 16.08.2026 - ראו הסעיף
  הבא) - כל תמונה נשמרת ישירות כ-JPEG באיכות 80 (`page.locator(...).screenshot(type="jpeg", quality=80)`),
  לא PNG שהומר בדיעבד.

**חשוב:** קבצי ה-GPX המקוריים עצמם *נשארים בינתיים* תחת `GPX_files/` (לא הועברו
ל-`data/`) - חלוקת התיקיות הסופית של הפרויקט (האם המסלולים הגולמיים יעברו
ל-`data/routes/`, איפה בדיוק ישבו דפי האתר עצמם וכו') עוד לא סוכמה ולא בוצעה.
`gpx_path` בתוך הקטלוג מצביע למיקום הנוכחי בפועל (`GPX_files/<שם>.gpx`) - יש
לעדכן את הסקריפט אם/כשהמיקום ישתנה.

## תיקון נוסף ב-`gpx_meaningful_rename.py` — עוד קודי-אפליקציה (16.08.2026)

לפני ייבוא 538 הקבצים (סעיף למעלה) נבדקו במפורש כל התחיליות (כמו `hk`) שהאפליקציה
משתמשת בהן בשמות קבצים אוטומטיים: `st`, `fi`, `ic`, `db`, `id` - כולן נוספו
מראש ל-`NOISE_WORDS_EN`, לפני ההרצה, כדי שלא יקרה שוב מה שקרה עם `hk` (סעיף
הבא): קבצים רבים שנשארים עם שם קריפטי כי `has_meaningful_word()` מזהה בטעות
את קוד-האפליקציה כ"מילה משמעותית". **הסתייגות ידועה:** קבצים מסוג `fi_<UUID>`
(8 קבצים) עדיין עלולים "לחמוק" מהזיהוי הזה בגלל UUID אקראי שמכיל במקרה רצף
אותיות בן 2+ (למשל `fi_E9B8658A-...` - זה בדיוק המקרה שתוקן ידנית קודם, ראו

## תיקון ידני לסיווג האוטומטי - `support_data/route_overrides.json` (05.10.2026)

`gpx_analyzer.py` מנחש סוג פעילות (הליכה/רכיבה, לפי מהירות) וסוג מקור
(הקלטה/תכנון, לפי timestamps). הניחוש שגוי לקבצים שהורדו ממקור חיצוני - נצפה
בפועל בקטעי **שביל ישראל לאופניים** (`ibt*.gpx`): חלקם נושאים timestamps של מי
שהקליט אותם במקור (וזוהו כ"הקלטה"), וחלקם בקצב שנראה כמו הליכה. הקובץ מאפשר
לכפות את הערכים לפי תבנית שם קובץ:

```json
{ "rules": [ { "pattern": "ibt*.gpx", "activity": "רכיבת אופניים", "source": "תכנון מסלול", "reason": "..." } ] }
```

- `pattern` - תבנית `fnmatch` על שם הקובץ, **לא תלויה באותיות גדולות/קטנות**
  (`ibt*` תופס גם `IBT1_...`). כמה כללים שתואמים לאותו קובץ מתמזגים לפי הסדר
  (המאוחר גובר). `reason` - תיעוד בלבד.
- ערכים מותרים: `activity` = `רכיבת אופניים` / `הליכה רגלית`; `source` = `הקלטה` /
  `תכנון מסלול`. ערך אחר עוצר את הבנייה עם שגיאה (ולכן גם את ה-commit), במקום
  להכניס לקטלוג תווית שהדף לא מכיר.
- `source: "תכנון מסלול"` משפיע גם על העיבוד, לא רק על התווית: מסלול מתוכנן
  **לא עובר ניקוי קפיצות GPS** ולא מסומן "לא תקין" (ראו `build_catalog_record()`).
- **שינוי בכלל מנתח מחדש את הקבצים שהוא נוגע בהם** גם בלי שינוי בקבצים עצמם -
  הכלל שהוחל נשמר במטמון (`catalog_build_cache.json`, שדה `override`) ומושווה
  בכל הרצה.
- מה הכלל **לא** משנה: תאריך. קבצי תכנון בלי timestamps (למשל `IBT1`, `IBT2`,
  `ibt6`) מקבלים את תאריך שינוי הקובץ (מועד ההעתקה לתיקייה). כדי לקבוע תאריך
  אחר - להוסיף אותו לשם הקובץ (`YYYY-MM-DD`).

| עמודה | תוכן |
|---|---|
| תאריך | לתיעוד בלבד - הסקריפט מתעלם ממנה |

  מיקום - אפשר לשנות סדר עמודות, אבל לא להסיר את המילים האלה מהכותרות.
- שם קובץ מאפשר לכתוב שורה למסלול חדש **לפני** שיש לו מספר בקטלוג.
- **הגיליון חייב להישאר משותף "כל מי שיש לו את הקישור יכול לצפות"** - הסקריפט
  שולף אותו דרך כתובת הייצוא הציבורית (CSV), בלי מפתחות. זה לא חושף מידע חדש -
  ההערות מוצגות ממילא באתר הציבורי. אם השיתוף יבוטל, הסקריפט יזהה שהתקבל דף
  התחברות במקום CSV וייכשל בלי לגעת בקובץ.

### `sync_route_notes.py` - מהגיליון לקובץ

```
python sync_route_notes.py            # שליפה וכתיבה
python sync_route_notes.py --check    # הצגת השינויים בלבד
```

- בונה מחדש **במלואו** את `route_catalog/data/route-notes.json` מהגיליון - הערה
  שנמחקה מהגיליון נמחקת גם מהאתר. מדפיס מה נוסף/עודכן/נמחק, ולא כותב את הקובץ
  אם אין שינוי.
- מתרגם שם קובץ למספר מסלול לפי `routes-catalog.json` - **לכן רץ אחרי**
  `build_routes_catalog.py`.
- **אזהרות** (השורה מדולגת, השאר נכתב): שם/מספר שלא נמצא בקטלוג, שורה בלי
  שם/מספר, ומסלול שמופיע בשתי שורות (האחרונה גוברת). שורה ששני שדות התוכן שלה
  ריקים - מדולגת בשקט.
- כישלון בשליפה (אין רשת, שיתוף בוטל) - קוד יציאה 2, הקובץ לא נגעו בו.
- **מזהה הגיליון מופיע בשני מקומות:** `SHEET_ID` כאן ו-`NOTES_SHEET_URL` בתוך
  `catalog.html` (קישור העריכה). אם מחליפים גיליון - לעדכן בשניהם.
- **pre-commit:** רץ אוטומטית מיד אחרי `build_routes_catalog.py` בכל commit
  שכולל שינוי GPX (ראו `.githooks/README.md`). כישלון בו לא מבטל את ה-commit.
  **commit בלי שינוי GPX לא מסנכרן** - לעדכון הערות בלבד יש להריץ את הסקריפט
  ידנית ואז לבצע commit.

**התהליך בפועל:** מוסיפים GPX לתיקייה → כותבים שורה בגיליון (אפשר לפי שם הקובץ)
→ commit + push. לעדכון הערה בלבד: עורכים בגיליון → מריצים את הסקריפט → commit + push.

### קובץ הנתונים - `route_catalog/data/route-notes.json`

```json
{
  "725": { "text": "טקסט חופשי, אפשר כמה שורות", "places": "מצודת יחיעם, מעיין עין יעקב. תצפית" }
}
```

- **תוצר בלבד - לא לערוך ידנית**, כל עריכה נדרסת בסנכרון הבא.
- **קובץ נפרד מ-`routes-catalog.json` במכוון** - `build_routes_catalog.py` בונה את
  הקטלוג מאפס, והיה מוחק כל הערה ששמורה בתוכו.
- **המפתח הוא מספר המסלול (`id`)**, יציב גם אחרי שינוי שם קובץ GPX (`route_ids.json`
  מזהה מסלול לפי תוכן). שימו לב: שורה בגיליון שכתובה לפי **שם קובץ** תפסיק
  להתאים אם שם הקובץ משתנה - הסקריפט יזהיר עליה; עדיף לעדכן אותה למספר המסלול.
- `places` נשמר כמחרוזת כפי שהוקלדה; הפיצול למקומות (לפי `.` או `,`) קורה בזמן
  ריצה ב-`getPlaces()` בתוך `catalog.html`.
- קובץ חסר/פגום לא מפיל את הקטלוג - הוא נטען כרגיל, פשוט בלי הערות.

### תצוגה וחיפוש (`catalog.html`)

- ההערה מוצגת בגוף האקורדיון (בפתיחת פרטי המסלול), מתחת לפרטים הקיימים:
  הטקסט החופשי (כולל ירידות שורה), ומקומות העניין כתגיות. מסלול בלי הערה - אין
  שום שינוי בתצוגה שלו.
- **לחיצה על תגית מבצעת חיפוש לפי הטקסט שלה**: ממלאת את שדה החיפוש, מחזירה
  לעמוד 1, מוסיפה ל"חיפושים אחרונים" וגוללת לראש הדף. ממומש במאזין קליק יחיד
  מואצל על `.place-tag` (לא `onclick` בתוך ה-HTML, כדי לא להכניס את שם המקום
  למחרוזת JS).
- **החיפוש כולל את מקומות העניין, ולא את הטקסט החופשי** (לפי בקשה) - נוספו
  ל-`haystack` בתוך `getFiltered()`. חיפוש בכמה מונחים מופרדים בפסיק ממשיך לעבוד
  כמו קודם ("וגם").
- **גובה האקורדיון הפתוח:** היה קבוע ב-CSS (`max-height:600px`) - הערה ארוכה הייתה
  נחתכת. `refreshAccHeight()` (נקראת מ-`toggleAcc()`) מנפישה את הפתיחה עד גובה
  התוכן, ובסוף האנימציה (`transitionend`) משחררת את הגובה ל-`none`, כך ששינוי
  רוחב חלון לא חותך תוכן. הסגירה ממשיכה להיות מונפשת.
- **כפתור "✏️ עריכת הערות"** ליד "הורדת קובץ GPX" פותח את הגיליון בטאב חדש. מוצג
  **רק** כשהדף נפתח מ-`127.0.0.1`/`localhost` (Live Server, `IS_LOCAL_EDIT`) - לא
  באתר החי.

## רשת מסלולים קיימים באזור - `gps_upload.html` (22.10.2026)

בעמוד "עריכת מסלול חדש" (`YR1/bike/gps_upload/gps_upload.html`, נפתח מכפתור
"🔎 בדיקת קובץ חדש" בקטלוג) נוסף כפתור **"🔲 רשת מסלולים קיימים באזור"**:
בוחרים מלבן בשתי לחיצות על המפה (פינות נגדיות), והעמוד מציג את כל הקטעים מכל

- **מקור הנתונים: `data/routes-tracks.json`** (הקווים המפושטים, ראו הסעיף על

  כיוון תנועה ובלי סדר בין המקטעים. מסלול שיוצא מהמלבן ונכנס שוב נותן שני
  מקטעים. קטע שחוצה את גבול המלבן נחתך בדיוק על הגבול (Liang-Barsky,

- **"הסרת חפיפות"** (תיבת סימון, מסומנת כברירת מחדל; `dedupSegments()`) - אזור
  שרוכבים בו הרבה מכיל את אותם שבילים עשרות פעמים (נבדק: רשת באזור קורן-כברי,
  209 מקטעים / 430 ק"מ, 98% מהאורך חופף). המקטעים עוברים מהארוך לקצר, וכל חלק
  שנמצא עד `AREA_DEDUP_TOL_M = 15` מ' מקו שכבר נשמר מושמט (כולל הלוך-חזור בתוך
  אותו מקטע); שאריות קצרות מ-`AREA_DEDUP_MIN_PIECE_M = 30` מ' מושמטות. באותה
  רשת: 27.4 ק"מ ב-48 קטעים. **למה 15 מ'** - זו סבולת הפישוט של `routes-tracks.json`;
  נבדק גם 10 ו-5 מ': שם אותו כביש נשאר כצרור קווים מקבילים (32.7 / 47.7 ק"מ).
  מחיר: שני שבילים שונים במרחק פחות מ-15 מ' זה מזה יתמזגו לקו אחד. ברשת צפופה
  מספר הקטעים יכול לעלות (מקטעים נחתכים לחתיכות), גם כשהאורך יורד בהרבה.
  החלפת התיבה מחשבת מחדש בלי בחירת אזור חדשה.
- **הגבלת גודל:** `AREA_MAX_SIDE_KM = 20` (צלע מקסימלית). המלבן בתצוגה המקדימה
  נצבע אדום כשהוא גדול מדי; לחיצה שנייה על מלבן גדול מדי לא מסיימת את הבחירה -
  הפינה הראשונה נשמרת ואפשר ללחוץ שוב על פינה קרובה יותר.
- הכתיבה לקובץ: `RouteEditor.buildGpxTextSegments()`/`downloadGpxSegments()`
  ב-`data/route_editor.js` (חדשות; `buildGpxText()` הקיימת היא עכשיו מקרה פרטי
  שלהן עם מקטע אחד, והפלט שלה לא השתנה).
- הרשת היא תצוגה+הורדה בלבד - היא **לא** מחוברת כבריכת הצמדה למצבי העריכה.

### הצגת קובץ GPX עם כמה מקטעים ב-`gps_upload.html` (22.10.2026)

`parseGpx()` מחזירה עכשיו רשימת מקטעים (`<trkseg>`), לא רשימת נקודות שטוחה:
כל מקטע מצויר כקו נפרד (multi-polyline), המרחק מחושב רק בתוך המקטעים, ולקובץ עם
יותר ממקטע אחד אין סימוני התחלה/סוף ויש תגית "🧩 N מקטעים" בכרטיס. לפני זה רשת
שהורדה ונטענה מחדש צוירה עם קווים ישרים בין סוף מקטע לתחילת הבא (ברשת קורן:
308.8 ק"מ "קפיצות" מתוך 739.5 שהוצגו). בבריכת "חיתוך מקטע" ו"מיזוג" כל מקטע הוא
קבוצה נפרדת (`routeIdx`, `allRouteSegments()`), כך שהחיתוך לא הולך בין מקטעים.

## קבצים עם כמה מקטעים בקטלוג (22.10.2026)

עד תאריך זה גם `build_routes_catalog.py` קרא את כל הנקודות כקו רציף אחד. רשת
`רשת_מסלולים_קורן2.gpx` (#751) נכנסה לקטלוג עם תמונה ממוזערת מלאה קווים ישרים
בין מקטעים, מרחק 196 ק"מ (במקום 48.5), וקו ב-`routes-tracks.json` שחיפוש לפי
קורדינטות "מצא" גם לאורך הקפיצות.

- `extract_track_points()` מתייגת כל נקודה ב-`seg` (אינדקס ה-`<trkseg>`).
  `split_segments()` מחזירה את אינדקסי ההתחלה של מקטעים נפרדים - **רק כשהפער בין
  סוף מקטע לתחילת הבא גדול מ-`SEGMENT_JOIN_MAX_GAP_M = 25` מ'**. מקטעים סמוכים
  מאוחדים לקו אחד: נבדק - 38 קבצים בקטלוג עם יותר ממקטע אחד, כמעט כולם הקלטה עם
  השהיה/המשך (פער של עד 20 מ'), והם נשארו בדיוק כמו קודם. אותו סף בדיוק ב-
  `joinCloseSegments()` ב-`data/route_editor.js` (צד הדפדפן) - **לשנות בשניהם יחד**.
- ניקוי קפיצות GPS עדיין רץ על כל הנקודות ברצף (כמו קודם) - החלוקה למקטעים אחריו.
- `distance_km` = סכום המרחקים בתוך המקטעים. התמונה הממוזערת (`renderTrack(coords,
  segmentStarts)` ב-`thumbnail_template.html`) מציירת כל מקטע בנפרד, בלי סימוני
  התחלה/סיום.
- **`routes-tracks.json`:** מסלול עם כמה מקטעים נכתב כמערך של מערכים שטוחים,
  `"751":[[lat,lon,...],[lat,lon,...]]`, כל מקטע מפושט בנפרד; מסלול רגיל נשאר
  `[lat,lon,...]`. שני הצרכנים (`routeDistanceKm()` ב-`catalog.html`,
  `clipTracksToBox()` ב-`gps_upload.html`) מזהים את שתי הצורות.
- `catalog.html`, תצוגת "מסלולים על המפה": `parseGpxSegments()` (במקום
  `parseGpxPoints`/`parseGpxPointsFull`) - כל מקטע קו נפרד, סימוני התחלה/סיום רק
  למקטע יחיד, ובבריכת החיתוך/מיזוג כל מקטע קבוצה נפרדת.
- `_segment_starts` נשמר ברשומה שבמטמון (`catalog_build_cache.json`); רשומה בלעדיו
  מנותחת מחדש (קרה פעם אחת לכל 607 הקבצים). תמונה ממוזערת של מסלול שנותח מחדש
  ויש לו כמה מקטעים נמחקת ונוצרת מחדש (`invalidate_thumbnails_for_segmented_routes()`).
- **תוצאה בפועל:** השתנו 4 מסלולים בלבד - #751 (196 → 48.5 ק"מ), `פוקהרה_1`
  (73.1 → 41.7), `נאות הכיכר_נווה זוהר` (39.1 → 34.3), `פוקהרה` (42.2 → 42.0).
- **לא תוקן:** `gpx_cleaner.html` עדיין קורא קובץ עם כמה מקטעים כקו אחד (והוא גם
  כותב את הקובץ חזרה מתוך `<trkseg>` יחיד).

## זיהוי נסיעה ברכב בתוך הקלטה (25.10.2026)

הקלטה שנשארה דולקת ברכב היא **טעות**: נסיעה בהתחלה/בסוף צריכה להיחתך, ו"רכיבה-נסיעה-רכיבה"
צריכה להתחלק לשני מסלולי רכיבה נפרדים. בשלב הזה רק **מזהים ומסמנים** - הקבצים לא משתנים.

- **`detect_driving()`** ב-`build_routes_catalog.py` רץ על הנקודות אחרי `clean_track_points()`
  (קפיצות GPS כבר הוסרו), רק בהקלטות (לא ב"תכנון מסלול"). לכל נקודה נבדק חלון של 2 דקות
  סביבה: נסיעה אם המהירות הממוצעת בחלון מעל 40 קמ"ש **בלי ירידה** (עד 5 מ'), או מעל 70 קמ"ש
  בכל מצב. רצף נסיעה נשמר רק אם הוא נמשך לפחות דקה **וגם** חציון המהירות בין נקודות עוקבות
  בתוכו מעל 40.
- **למה כך - נבדק על כל 493 ההקלטות:**
  - ממוצע פשוט (45 קמ"ש) סימן 73 מסלולים - כמעט כולם הירידה המהירה מגעתון באופניים. התנאי
    "בלי ירידה" (רכב מהיר גם במישור ובעלייה, אופניים רק בירידה) הוריד ל-9.
  - סף נפרד להליכה (15 קמ"ש) סימן 22 מסלולים בטעות - רכיבות של 30-44 ק"מ שמסווגות "הליכה".
    לכן סף אחד לכל המסלולים, כמו `CLEAN_MAX_SPEED_KMH`.
  - שאריות קפיצות GPS במסלולים "לא ברור (מהירות חריגה)" זוהו כנסיעה בגלל כמה צעדים ענקיים
    בודדים (190-307 קמ"ש) בתוך תנועה איטית (חציון 7-23). תנאי החציון מסנן אותן; בנסיעה
    אמיתית החציון היה 44-71.
  - **תוצאה: 5 מסלולים** - #42, #349, #354, #406, #428.
- **ברשומה:** `"driving": [{"start", "end" (ISO, UTC), "km"}]` - רשימה ריקה = תקין. בסוף כל
  הרצה הסקריפט מדפיס את רשימת המסלולים המסומנים, עם השעות והאורך.
- **מטמון:** רשומה במטמון בלי השדה מקבלת אותו ב-`driving_for_cached_record()` בלבד, בלי ניתוח
  מלא - ניתוח מלא היה מוחק את התמונות הממוזערות של כל מסלול עם ניקוי קפיצות/כמה מקטעים.
  כדי לחשב מחדש אחרי שינוי סף: למחוק את `driving` מכל הרשומות ב-`catalog_build_cache.json`.
- **בקטלוג (`catalog.html`):** `hasDriving()`/`isFaulty()` - מסלול עם נסיעה מוצג כמו "לא תקין":
  כרטיס אפור, תגית "🚗 כולל נסיעה ברכב", הערה בגוף הכרטיס עם השעות (בשעון המקומי) והאורך, ונדחק
  לתחתית הרשימה בכל מיון.
- **שימו לב:** הרצה עם `--skip-thumbnails` כותבת `"thumbnail": null` לכל המסלולים בקטלוג. אחרי
  בדיקה כזו יש להריץ שוב בלי הדגל לפני commit.

## טופס הוספת מסלול - `YR1/bike/add_route/add_route.html` (25.10.2026)

טופס ציבורי (קישור "➕ הוספת מסלול" בראש הקטלוג) שבו רוכב שולח קובץ GPX עם שם, הערות, מקומות
עניין ופרטי קשר. ההגשה מגיעה **במייל, עם קובץ ה-GPX המקורי מצורף**. שום דבר לא נכנס לקטלוג
אוטומטית - מוסיפים ידנית: הקובץ ל-`GPX_files/`, וההערות והמקומות לגיליון `route-notes`.

**הזרימה:** הדף -> `netlify/functions/bike-route-submit.js` (בודק מקור, גודל ושדות, מוסיף טוקן סודי
ו-IP) -> Google Apps Script (`netlify/bike-route-submit-apps-script.gs.js`: בודק טוקן, מגביל קצב
5 בשעה לכתובת IP ו-40 ביום, ושולח מייל מהחשבון שלך אליו).

- **בדפדפן, לפני השליחה:** בדיקה שהקובץ עד 5MB ושהוא GPX עם נקודות, תצוגה על מפה עם מרחק, טיפוס
  ותאריך, ואזהרה על נסיעה ברכב - אותו כלל כמו `detect_driving()` כאן, מועתק ל-JS (לא משותף).
- **דחיסה:** הדף דוחס את הקובץ ב-gzip (`CompressionStream`) לפני השליחה, כי Netlify מגביל גוף בקשה
  לפונקציה ל-6MB ו-base64 של קובץ 5MB הוא כ-6.7MB. נבדק: 3.8MB -> 231KB, ואחרי פריסה בצד ה-Apps
  Script הקובץ זהה בייט-לבייט למקור. דפדפן בלי `CompressionStream` שולח לא דחוס, עד 4MB.
- **ספאם:** שדה מלכודת מוסתר (`website`) - הגשה שבה הוא מלא מקבלת "הצלחה" ולא נשלחת; והגבלת הקצב
  ב-Apps Script (`CacheService`).

### הקמה - פעם אחת

1. **יצירת הסקריפט:** [script.google.com](https://script.google.com) (מחובר לחשבון שאליו יגיעו
   המיילים) -> **New project**. מוחקים את התוכן ההתחלתי ומדביקים את **כל** התוכן של
   `netlify/bike-route-submit-apps-script.gs.js`. נותנים שם לפרויקט (למעלה, "Untitled project"),
   למשל "טופס הוספת מסלול", ושומרים (Ctrl+S).
2. **הטוקן הסודי:** בתפריט השמאלי ⚙️ **Project Settings** -> בתחתית **Script Properties** ->
   **Add script property**. Property: `SECRET`, Value: מחרוזת אקראית ארוכה -> **Save script properties**.
3. **אישור הרשאות ומייל בדיקה:** חוזרים לעורך (<>), בוחרים בשורת הכלים למעלה את הפונקציה
   `testSetup` ולוחצים **Run**. נפתח חלון הרשאות: **Review permissions** -> בוחרים את החשבון ->
   "Google hasn't verified this app" -> **Advanced** -> **Go to … (unsafe)** -> **Allow**. אמור
   להגיע מייל "בדיקת טופס הוספת מסלול". (האזהרה רגילה לסקריפט פרטי שכתבת בעצמך.)
4. **פרסום:** **Deploy** -> **New deployment** -> ⚙️ ליד "Select type" -> **Web app**.
   Execute as: **Me**. Who has access: **Anyone** (חובה - הפונקציה ב-Netlify קוראת לו בלי התחברות;
   הטוקן הוא שמגן עליו). **Deploy** -> מעתיקים את **Web app URL** (מסתיים ב-`/exec`).
5. **Netlify:** Site configuration -> **Environment variables** -> **Add a variable**, פעמיים:
   - `BIKE_ROUTE_SUBMIT_URL` = הכתובת מסעיף 4
   - `BIKE_ROUTE_SUBMIT_SECRET` = אותו ערך של `SECRET` מסעיף 2 (לסמן "Contains secret values")
6. **פריסה מחדש:** משתני סביבה נכנסים לתוקף רק בפריסה הבאה - Deploys -> **Trigger deploy** ->
   **Deploy site** (או כל push).
7. **בדיקה:** לשלוח מסלול קטן מהטופס באתר החי ולוודא שהגיע מייל עם הקובץ מצורף.

**עדכון הסקריפט בעתיד:** אחרי עריכה בעורך: Deploy -> **Manage deployments** -> ✏️ -> Version:
**New version** -> Deploy. כך הכתובת נשארת אותה כתובת (New deployment יוצר כתובת חדשה, ואז צריך
לעדכן גם את `BIKE_ROUTE_SUBMIT_URL`).

**לפני ההקמה** הטופס מחזיר "שליחת הטופס עדיין לא הוגדרה באתר" (503) - בלי שגיאה אחרת.
